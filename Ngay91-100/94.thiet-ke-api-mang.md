## Thiết kế API mạng

Hiện nay nhiều ứng dụng web và ứng dụng di động đều sử dụng mô hình phát triển tách biệt front-end và back-end. Nói một cách đơn giản, tách biệt front-end và back-end nghĩa là phía front-end hoặc ứng dụng di động tương tác với back-end thông qua các giao diện API mạng, nhận dữ liệu do API cung cấp và chịu trách nhiệm render giao diện người dùng. API là viết tắt của Application Programming Interface (giao diện lập trình ứng dụng), API mạng thường đề cập đến tài nguyên có thể truy cập được thông qua một URL (Uniform Resource Locator), tức là qua URL này chúng ta có thể yêu cầu máy chủ thực hiện thao tác đối với một tài nguyên nào đó và trả về kết quả thao tác. Mọi người có thể nghĩ xem, chẳng phải giao diện API mạng cũng là một dạng đóng gói hay sao? Nói một cách đơn giản, đó chính là ẩn giấu logic nghiệp vụ phức tạp đằng sau các giao diện API đơn giản.

Định dạng chung của URL như sau:

```
giao_thuc://ten_nguoi_dung:mat_khau@host:port/duong_dan_1/.../duong_dan_N/ten_tai_nguyen
```

> **Giải thích**: Trong URL, tên người dùng (có thể không cần cung cấp), mật khẩu (có thể không cần cung cấp), cổng (có thể sử dụng cổng mặc định), đường dẫn (tài nguyên có thể nằm trực tiếp ở đường dẫn gốc `/`) không phải là các phần bắt buộc, có thể thiết lập tùy theo nhu cầu.

API mạng thường được truy cập dựa trên HTTP hoặc HTTPS. Điểm thuận lợi lớn nhất của việc dựa trên HTTP/HTTPS là việc truy cập vô cùng đơn giản, thuận tiện, đồng thời có thể truy cập và tương tác giữa các ngôn ngữ và các ứng dụng khác nhau.

### Nguyên tắc thiết kế

#### Vấn đề then chốt

Một nguyên tắc rất quan trọng khi thiết kế giao diện API mạng cho ứng dụng di động hoặc PC là: **Thiết kế giao diện API dựa trên thực thể nghiệp vụ chứ không dựa trên giao diện người dùng hay thao tác của người dùng**. Nếu việc thiết kế giao diện API dựa theo thao tác của người dùng hoặc các thiết lập chức năng trên giao diện, thì khi yêu cầu nghiệp vụ thay đổi, giao diện người dùng cũng sẽ điều chỉnh, dữ liệu cần thiết cũng thay đổi theo, khiến cho nhà phát triển back-end phải liên tục sửa đổi API, hoặc thiết kế nhiều phiên bản cho một API, tất cả những điều này đều làm tăng chi phí phát triển và bảo trì dự án. Chúng ta có thể hiểu thực thể nghiệp vụ là tài nguyên do máy chủ cung cấp, còn URL chính là bộ định vị (mã định danh) của tài nguyên, cách làm này là đơn giản và tự nhiên nhất. Đối với các thao tác người dùng tương đối phức tạp, chúng ta có thể cung cấp một "Facade" (mẫu thiết kế Facade Pattern), thông qua Facade này để kết hợp các chức năng của nhiều API lại với nhau là được.

Dưới đây là các giao diện API mở của một trang web, có thể thấy việc thiết kế API được tiến hành xoay quanh các thực thể nghiệp vụ, và đều đạt được tiêu chí "nhìn tên biết ý nghĩa".

| Bình luận | |
| --- | --- |
| comments/show | Lấy danh sách bình luận của một bài viết |
| comments/by_me | Danh sách bình luận của chính mình |
| comments/to_me | Danh sách bình luận nhận được |
| comments/mentions | Danh sách bình luận có @ mình |
| comments/create | Tạo một bình luận mới |
| comments/destroy | Xóa một bình luận |
| comments/reply | Trả lời một bình luận |

Cần lưu ý rằng, **các giao diện API ở trên không theo phong cách REST**. REST là một phong cách kiến trúc ứng dụng mạng, được coi là phù hợp nhất cho các ứng dụng mạng phân tán. Về kiến thức REST, bạn có thể đọc các bài viết của Ruan Yifeng: [Hiểu về kiến trúc RESTful](http://www.ruanyifeng.com/blog/2011/09/restful.html) cũng như [Hướng dẫn thiết kế RESTful API](http://www.ruanyifeng.com/blog/2014/05/restful_api.html). Tất nhiên, khi đọc hai bài viết này mọi người cũng nên tiếp cận với góc nhìn phản biện, vì các quan điểm được trình bày trong đó không hoàn toàn chuẩn xác, thậm chí có một số nội dung mâu thuẫn lẫn nhau.

Dữ liệu do giao diện API trả về thường có định dạng **JSON** hoặc **XML**, định dạng dữ liệu XML hiện nay cơ bản đã bị loại bỏ. Đối với dữ liệu định dạng JSON, chúng ta cần lưu ý không nên trả về các giá trị `null`, vì những giá trị như vậy một khi xử lý không khéo sẽ mang lại những phiền toái không cần thiết cho việc phát triển phía front-end và mobile (bởi lập trình viên có thể sử dụng ngôn ngữ định kiểu mạnh). Để giải quyết vấn đề này có thể bắt đầu từ gốc rễ: khi thiết kế cơ sở dữ liệu, cố gắng thêm ràng buộc `not null` cho mỗi trường hoặc thiết lập ràng buộc giá trị mặc định hợp lý.

#### Các vấn đề khác

1. Vấn đề thông báo cập nhật: Thiết kế một API luôn được truy cập đầu tiên mỗi khi mở hệ thống, API này sẽ trả về cho phía ứng dụng di động các thông tin liên quan đến việc cập nhật hệ thống, nhờ đó có thể nhắc nhở người dùng cập nhật App.
2. Vấn đề nâng cấp phiên bản: Khi nâng cấp phiên bản API, cần cân nhắc khả năng tương thích ngược với các phiên bản cũ, đồng thời cho phép cả phiên bản mới và phiên bản cũ đều có thể truy cập được. Có thể đưa thông tin phiên bản vào URL hoặc đặt số phiên bản trong phần header của giao thức HTTP(S). Về vấn đề này có rất nhiều tranh luận, nếu quan tâm bạn có thể xem thảo luận trên [Stack Overflow](https://stackoverflow.com/questions/972226/how-to-version-rest-uris).
3. Vấn đề kích thước ảnh: Thiết bị di động có thể cần các kích thước khác nhau cho cùng một hình ảnh, có thể truyền tham số kích thước khi lấy ảnh để nhận tài nguyên tương ứng; cách tốt hơn là sử dụng trực tiếp dịch vụ lưu trữ đám mây hoặc CDN (vốn đã cung cấp sẵn tính năng thu phóng ảnh), qua đó có thể tăng tốc độ truy cập tài nguyên.

### Viết tài liệu

Dưới đây lấy ví dụ thiết kế API bình luận để giải thích ngắn gọn cách viết tài liệu API.

Trước tiên, chúng ta có thể định nghĩa mã trạng thái trả về toàn cục.

| Mã trả về | Thông điệp trả về | Giải thích |
| --- | --- | --- |
| 10000 | Lấy bình luận thành công | |
| 10001 | Tạo bình luận thành công | |
| 10002 | Không thể tạo bình luận | Không thể tạo bình luận do vi phạm cơ chế kiểm duyệt khi tạo |
| 10003 | Bình luận đã bị xóa | Khi xem bình luận thì bình luận đã bị xóa do chứa yếu tố không phù hợp |
| 10004 | ... | ... |

1. Lấy bình luận bài viết.

   **GET** `/articles/{article-id}/comments/`

   Nhà phát triển: Vương Đại Chùy

   Thời gian cập nhật lần cuối: Ngày 10 tháng 8 năm 2018

   Tag: v 1.0

   Mô tả giao diện: Lấy toàn bộ bình luận của bài viết được chỉ định

   Hướng dẫn sử dụng: Mặc định trả về 20 bản ghi dữ liệu, cần thiết lập mã định danh (key) trong request header

   Tham số request:

   | Tên tham số | Kiểu | Bắt buộc | Vị trí tham số | Giải thích |
   | --- | --- | --- | --- | --- |
   | page | Số nguyên | Không | Tham số truy vấn (query) | Số trang, giá trị mặc định là 1 |
   | size | Số nguyên | Không | Tham số truy vấn (query) | Số lượng bình luận lấy mỗi lần (10~100), giá trị mặc định là 20 |
   | key | Chuỗi | Có | Request header | Mã định danh của người dùng |

   Thông tin response:

   ```JSON
   {
       "code": 10000,
       "message": "Lấy bình luận thành công",
       "page": 1,
       "size": 10,
       "totalPage": 35,
       "contents": [
           {
               "userId": 1700095,
               "nickname": "Vương Đại Chùy",
               "pubDate": "2018-07-31",
               "content": "Admin có bị làm sao không vậy",
               /* ... */
           },
           {
           	"userId": 1995322,
               "nickname": "Bạch Nguyên Phương",
               "pubDate": "2018-08-02",
               "content": "Bác ở trên nói hay lắm",
               /* ... */
           }
       ]
       /* ... */
   }
   ```

2. Thêm mới bình luận bài viết.

   **POST** `/articles/{article-id}/comments`

   Nhà phát triển: Vương Đại Chùy

   Thời gian cập nhật lần cuối: Ngày 10 tháng 8 năm 2018

   Tag: v 1.0

   Mô tả giao diện: Tạo bình luận cho bài viết được chỉ định

   Hướng dẫn sử dụng: Tạm thời chưa có

   Tham số request:

   | Tên tham số | Kiểu | Bắt buộc | Vị trí tham số | Giải thích |
   | --- | --- | --- | --- | --- |
   | userId | Chuỗi | Có | Request body | ID người dùng |
   | key | Chuỗi | Có | Request header | Token của người dùng |
   | content | Chuỗi | Có | Request body | Nội dung bình luận |

   Thông tin response:

   ```JSON
   {
       "code": 10001,
       "message": "Tạo bình luận thành công",
       "comment": {
           "pubDate": "2018-07-31",
           "content": "Admin có bị làm sao không vậy"
           /* ... */
       }
       /* ... */
   }
   ```

> **Gợi ý**: Nếu chưa có kinh nghiệm viết tài liệu API, bạn có thể sử dụng các nền tảng soạn thảo tài liệu API trực tuyến như [RAP2](http://rap2.taobao.org/) hoặc [YAPI](http://yapi.demo.qunar.com/) để tiến hành viết tài liệu API.
